# Phase 260810-f21: Code Review Report

**Reviewed:** 2026-08-10
**Depth:** deep (cross-file trace of every existing write path to `Venda.custoEnvio`)
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the new Uber Direct "capture real delivery cost" feature: the pure
interpretation module (`uber-custo-entrega.ts`), the client/persistence module
(`uber-entrega.ts`), the admin API route, the schema/migration, and the three
new test files. The money-in-cents-to-reais conversion, the currency guard,
the admin-only RBAC check, the P2002 idempotency handling, and the
"never write to `Despesa`" invariant are all correctly implemented and
covered by tests.

The most serious problem is not inside the new files themselves but in how
they interact with three pre-existing write paths to `Venda.custoEnvio`
(`historico/actions.ts:updateVenda`, `venda-rapida/actions.ts`,
`ai-actions.ts:atualizar_venda`): none of them know about the new
`custoEnvioFonte` column, so they can silently leave a stale
`"uber_final"` label on a value a human has since overwritten by hand — which
then lets a later, legitimate Uber reconciliation call silently clobber that
human correction, defeating the exact overwrite-protection guarantee this
feature was built to provide (T-F21-04). A handful of narrower gaps
(TOCTOU race between read-decide-write, missing venda-status check, an
unhandled-exception path, loose `Number()` coercion on `vendaId`, and an
untested OAuth code path) round out the warnings.

## Critical Issues

### CR-01: `custoEnvioFonte` is not updated by the other three code paths that write `Venda.custoEnvio`, letting a stale "uber_final" label survive a manual correction and be silently overwritten later

**File:** `src/lib/uber-custo-entrega.ts:751-771` (`decidirGravacaoCustoEnvio`) interacting with:
- `src/app/(app)/historico/actions.ts:64-81` (`updateVenda`)
- `src/app/(app)/venda-rapida/actions.ts:459` (edit action)
- `src/lib/ai-actions.ts:1015-1029` (`atualizar_venda` AI tool)

**Issue:**
`decidirGravacaoCustoEnvio` treats `custoEnvioFonte === "uber_final"` as proof
that the current `custoEnvio` value is Uber-verified and allows a new
*definitivo* Uber read to overwrite it unconditionally (the "reconciliation"
branch, tested in `uber-custo-envio-decisao.test.ts` Teste 6). But none of
the three existing places that can write `Venda.custoEnvio`
(`updateVenda` in `historico/actions.ts`, the equivalent action in
`venda-rapida/actions.ts`, and the `atualizar_venda` AI chat tool in
`ai-actions.ts`) touch `custoEnvioFonte` at all — Prisma `update()` only
changes fields present in `data`, so the column is left exactly as it was.

Concrete failure sequence:
1. Admin captures the real Uber cost for venda #50 via the new route:
   `custoEnvio = 24.90`, `custoEnvioFonte = "uber_final"`.
2. A finance user disputes the Uber charge and manually corrects the freight
   cost to `30.00` through the normal "editar venda" screen
   (`historico/actions.ts:updateVenda`, or the AI chat "atualizar_venda"
   tool). This write only sets `custoEnvio: envio`; `custoEnvioFonte` still
   reads `"uber_final"` in the database — now a lie.
3. Someone re-runs the capture-cost route for the same `deliveryId` (e.g. a
   retry, or a future reconciliation batch job built on top of this API).
   `decidirGravacaoCustoEnvio` sees `fonteAtual === "uber_final"` and
   `novoDefinitivo === true`, and takes the "already final, but this is a
   reconciliation of the same delivery" branch → `gravar: true` → the
   human's manually-corrected `30.00` is silently overwritten back to
   Uber's `24.90`, with no warning, no conflict, no log distinguishable from
   a normal reconciliation.

This defeats the stated purpose of the feature (T-F21-04: "custo digitado a
mão... nunca é sobrescrito") in the one scenario it exists to prevent —
just delayed by one edit cycle instead of happening on the very next call.
The inverse also happens: a manual `custoEnvio` edit made on a venda that
still has `custoEnvioFonte = null` and `custoEnvio > 0` is correctly
protected (`custo_manual_preservado`), but as soon as any Uber capture ever
touches that venda even once, the protection permanently degrades because
none of the edit surfaces can put the column back to `null` or `"manual"`.

**Fix:** Either (a) have `historico/actions.ts:updateVenda`,
`venda-rapida/actions.ts`, and `ai-actions.ts:atualizar_venda` reset
`custoEnvioFonte` to `null` (or an explicit `"manual"` value already listed
in the column's own doc comment) whenever they change `custoEnvio` and the
caller isn't this Uber integration, e.g.:

```ts
// historico/actions.ts, venda-rapida/actions.ts, ai-actions.ts atualizar_venda
data: {
  ...,
  custoEnvio: envio,
  custoEnvioFonte: null, // uma edicao manual sempre reseta a proveniencia
},
```

or (b) add a `dbUpdatedAt`-style guard/transaction so `registrarCustoEntregaUber`
only trusts `custoEnvioFonte` if it also verifies `custoEnvio` hasn't diverged
from what it last wrote (store the last-known value together with the
source). Option (a) is the minimal, consistent-with-existing-code fix.

## Warnings

### WR-01: `registrarCustoEntregaUber` reads-then-writes without any concurrency guard — a genuine (if narrow) race can downgrade a "final" cost to a "provisional" one

**File:** `src/lib/uber-entrega.ts:957-986`

**Issue:** `registrarCustoEntregaUber` does `findUnique` → `decidirGravacaoCustoEnvio`
(pure decision based on that read) → `update`, with no transaction, no
`SELECT ... FOR UPDATE`, and no `WHERE` clause tying the `update` back to the
state that was read. If two requests for the *same delivery* race — e.g. an
admin double-triggers the capture right as Uber's delivery status flips from
`en_route_to_dropoff` to `delivered` — both can read the venda in its old
state (`custoEnvioFonte: null`, `custoEnvio: 0`) before either commits. If
the request carrying the **earlier, non-final** Uber read happens to *commit
second*, it overwrites the row with `custoEnvioFonte: "uber_provisorio"`
after the other request already committed `"uber_final"`, silently
downgrading a value this feature is specifically supposed to protect
(T-F21-04). The much more common "double click" case (identical
`deliveryId` + identical result) is harmless because both writes are
idempotent, but the state-transition race is real and money-affecting.

**Fix:** Make the decision-then-write atomic, e.g. wrap in
`prisma.$transaction` and re-read the row for update, or add the decision as
a conditional `WHERE` on the update itself:

```ts
const upd = await prisma.venda.updateMany({
  where: {
    id: vendaId,
    OR: [
      { custoEnvioFonte: null, custoEnvio: { lte: 0 } },
      { custoEnvioFonte: "uber_provisorio" },
      ...(resultado.definitivo ? [{ custoEnvioFonte: "uber_final" }] : []),
    ],
  },
  data: { custoEnvio: resultado.total, uberDeliveryId: resultado.deliveryId, custoEnvioFonte: decisao.fonteResultante },
});
if (upd.count === 0) { /* someone else already decided differently — re-read and report */ }
```

### WR-02: No check that the venda isn't `cancelada`/`estornada` before binding a delivery cost to it — permanently burns the unique `deliveryId` slot on the wrong sale

**File:** `src/app/api/frete/uber/custo/route.ts:538-541`

**Issue:** The route only checks that the venda exists
(`prisma.venda.findUnique({ where: { id: vendaIdNum }, select: { id: true } })`)
— it never checks `status`. Two existing call sites in this same codebase
filter out `cancelada`/`estornada` before touching a venda financially
(`src/app/api/admin/backfill-estoque/route.ts:16`,
`src/app/api/clientes/[id]/limite/route.ts:26`), so this route is an outlier.
Concrete scenario: an operator typos the venda id and it happens to match a
cancelled sale that still exists in the table. The API returns 200, writes
`custoEnvio`/`uberDeliveryId` on the cancelled venda. Because `finance.ts`
already excludes cancelled/estornada sales from `freteReal`, the DRE isn't
corrupted directly — but the `uberDeliveryId` unique index now permanently
points at the wrong (dead) sale, so the *correct* venda can never have this
same delivery cost registered again (`P2002` → 409 `entrega_ja_lancada`)
without a manual DB fix. There is no self-service recovery path in this API.

**Fix:** Select `status` in the existing `findUnique` and reject
`cancelada`/`estornada` the same way `backfill-estoque` and `limite` do:

```ts
const venda = await prisma.venda.findUnique({ where: { id: vendaIdNum }, select: { id: true, status: true } });
if (!venda) return NextResponse.json({ error: "Venda nao encontrada." }, { status: 404 });
if (venda.status === "cancelada" || venda.status === "estornada") {
  return NextResponse.json({ error: "Venda cancelada/estornada nao aceita custo de entrega." }, { status: 409 });
}
```

### WR-03: No top-level `try/catch` in the route; unexpected `prisma.venda.update` errors (e.g. `P2025`, connection failures) propagate unhandled instead of returning a JSON error like every other admin route

**File:** `src/app/api/frete/uber/custo/route.ts:508-557`, `src/lib/uber-entrega.ts:978-996`

**Issue:** `registrarCustoEntregaUber`'s `try/catch` only special-cases
`P2002`; any other error from `prisma.venda.update` (e.g. `P2025` if the
venda was deleted between the existence check and the update, a transient
DB error, etc.) is re-thrown (`throw err;`). `POST` in `route.ts` has **no**
surrounding `try/catch` at all, unlike every other admin route in this repo
(`backfill-estoque/route.ts` wraps its whole body and returns
`{ error: msg }` with status 500). The result is an unhandled rejection that
falls through to Next.js's generic error handling instead of the
project's consistent JSON error shape — and the error is never logged by
this module before it escapes (no `console.error` on the re-throw path).

**Fix:** Add a top-level try/catch in the route (or in
`registrarCustoEntregaUber`) that logs and returns a JSON 500 consistent with
the rest of the codebase:

```ts
try {
  const resultado = await registrarCustoEntregaUber({ config, vendaId: vendaIdNum, deliveryId: deliveryId.trim() });
  ...
} catch (err) {
  console.error("[frete/uber/custo] erro inesperado:", err);
  return NextResponse.json({ error: "Erro interno ao capturar custo de entrega." }, { status: 500 });
}
```

### WR-04: `Number(vendaId)` accepts arrays and booleans due to JS coercion, silently mistargeting the wrong sale instead of rejecting the request

**File:** `src/app/api/frete/uber/custo/route.ts:521-525`

**Issue:** `Number(vendaId)` is applied to an `unknown` value straight out of
the JSON body. JS numeric coercion has surprising special cases that pass
the subsequent `Number.isInteger(...) && > 0` check:

```
Number([7])   === 7    // single-element array coerces to its element
Number(true)  === 1    // boolean coerces to 0/1
```

So `{ "vendaId": [7], "deliveryId": "x" }` or `{ "vendaId": true, ... }`
(the latter silently targeting venda id `1`) both pass validation instead of
being rejected as malformed input. Low exploitability (the caller is already
an authenticated admin), but it's a real type-confusion gap in a route that
otherwise takes input validation seriously (`deliveryIdValido`, currency
checks, etc.), and a malformed client payload (e.g. a form bug sending an
array) would silently write to the wrong sale rather than failing loudly.

**Fix:** Validate the raw type before coercing:

```ts
if (typeof vendaId !== "number" && typeof vendaId !== "string") {
  return NextResponse.json({ error: "vendaId invalido." }, { status: 400 });
}
const vendaIdNum = Number(vendaId);
```

### WR-05: Missing `currency_code` on `full_fee` silently defaults to `"BRL"` instead of failing safe, bypassing the currency guard it sits right next to

**File:** `src/lib/uber-custo-entrega.ts:688-689`

**Issue:**
```ts
const moeda = typeof fullFee.currency_code === "string" && fullFee.currency_code ? fullFee.currency_code : "BRL";
if (moeda !== "BRL") return falha("moeda_inesperada", moeda);
```
The whole point of this check (per its own module doc comment and
`T-F21-02`) is to make sure a non-BRL amount is never written to
`Venda.custoEnvio` as if it were reais. But if `currency_code` is missing or
not a string, the code doesn't fail — it silently *assumes* BRL and proceeds
to convert and (potentially) persist the value. If Uber's API ever omits
`currency_code` for a reason other than "it's BRL" (schema change, a
different Uber product region, a proxy/gateway stripping the field), this
guard does nothing; it converts and writes the value as if the currency
check had passed.

**Fix:** Treat a missing/invalid `currency_code` as `resposta_incompleta`
rather than assuming BRL:

```ts
if (typeof fullFee.currency_code !== "string" || !fullFee.currency_code) {
  return falha("resposta_incompleta", "moeda_ausente");
}
if (fullFee.currency_code !== "BRL") return falha("moeda_inesperada", fullFee.currency_code);
```

### WR-06: Persisted `uberDeliveryId` comes from Uber's response body (`envelope.id`), not from the validated request `deliveryId` — a missing/odd `id` field writes an empty string into the unique column

**File:** `src/lib/uber-custo-entrega.ts:709-720`, `src/lib/uber-entrega.ts:982-985`

**Issue:** `interpretarCustoEntregaUber` builds `deliveryId:
typeof envelope.id === "string" ? envelope.id : ""` from the **response**
body, and `registrarCustoEntregaUber` persists that value
(`uberDeliveryId: resultado.deliveryId`) — not the already-validated
`deliveryId` parameter that was used to build the request URL
(`deliveryIdValido` + `encodeURIComponent`). If Uber's Get Delivery Status
response for some edge case doesn't echo `id` (or returns it under a
different shape), the code writes `""` into the `uber_delivery_id` unique
column instead of the real, known-good delivery id. The first such
occurrence succeeds (unique index allows one row with `""`); any later
occurrence for a different venda hits `P2002` and gets misreported as
`"entrega_ja_lancada"`, and the audit trail (`uberDeliveryId`) for the first
row is simply wrong. No test in this diff exercises `envelope.id` differing
from the requested `deliveryId`, so this path is unverified.

**Fix:** Persist the input `deliveryId` (already validated) rather than
trusting the response body for the identifier used as the DB key:

```ts
// uber-entrega.ts, registrarCustoEntregaUber
data: {
  custoEnvio: resultado.total,
  uberDeliveryId: deliveryId, // o parametro validado, nao resultado.deliveryId
  custoEnvioFonte: decisao.fonteResultante,
},
```

**File:** `src/__tests__/uber-custo-entrega-rota.test.ts`, `src/__tests__/uber-custo-envio-decisao.test.ts`

**Issue:** Both test files hardcode `CONFIG_ESTATICA = { source: "static_token", ... }`.
`resolveUberBearerToken`'s `oauth` branch, and the entire 401 →
`limparEntradaCacheTokenUber` → retry-with-fresh-token logic in
`buscarCustoEntregaUber` (`src/lib/uber-entrega.ts:872-885`) — the exact
behavior called out as a review focus area — is never exercised by any test
added in this diff. `getDeliveryQuote` in `uber.ts` has the identical
pattern and presumably has its own coverage from an earlier phase, but this
new module duplicates that logic and should have its own test proving the
retry actually happens and actually clears the right cache key
(`clientId + "::eats.deliveries"`).

**Fix:** Add a test with `CONFIG_ESTATICA_OAUTH = { source: "oauth", clientId, clientSecret, customerId }`
that mocks `fetch` to return 401 once then 200, and asserts
`limparEntradaCacheTokenUber` is invoked with the `"eats.deliveries"` scope
(not `"business.receipts"`) and that the second call succeeds.

### IN-02: `custoEnvioFonte` has no DB-level constraint restricting it to the three documented values

**File:** `prisma/schema.prisma:177-178`, `prisma/migrations/20260810120000_venda_uber_custo_entrega/migration.sql:22`

**Issue:** The column is a plain nullable `TEXT` with the allowed values
(`"manual" | "uber_provisorio" | "uber_final"`) documented only in a code
comment. `decidirGravacaoCustoEnvio` only special-cases the literal string
`"uber_final"`; any other non-null value (a typo introduced by a future
change, or literally the documented-but-never-actually-written `"manual"`
value) falls through to be treated the same as `"uber_provisorio"` — i.e.
always overwritable. Not exploitable today since nothing writes an
out-of-vocabulary value, but there's no guard rail stopping it from
happening silently in the future.

**Fix:** Add a `CHECK` constraint in a follow-up migration:
`ALTER TABLE "vendas" ADD CONSTRAINT custo_envio_fonte_valido CHECK (custo_envio_fonte IS NULL OR custo_envio_fonte IN ('manual','uber_provisorio','uber_final'));`

### IN-03: A manually-entered `custoEnvio = 0` is indistinguishable from "never set", so a later Uber capture silently overwrites an intentional free-shipping entry

**File:** `src/lib/uber-custo-entrega.ts:757-763`

**Issue:** `decidirGravacaoCustoEnvio`'s only signal that a value was
entered by hand is `fonteAtual === null && custoEnvioAtual > 0`. If an
operator manually records a legitimate `custoEnvio = 0` (e.g. a promotional
free-delivery sale) through the normal edit screen, `custoEnvioFonte` stays
`null` and `custoEnvioAtual` is `0` — indistinguishable from a venda that
simply never had a shipping cost recorded. A later Uber capture for that
venda will pass the "not manual" check and overwrite the intentional `0`
with whatever the Uber API reports. Narrow edge case, low severity.

**Fix:** Not blocking; if this scenario matters in practice, an explicit
`"manual"` sentinel (already documented in the column comment but never
actually written anywhere) written by the manual-edit paths would resolve
both this and CR-01 at once.

### IN-04: `normalizarCodigoTaxaUber`'s "protection" against free text only strips separators/case — recognizable substrings of leaked text still survive

**File:** `src/lib/uber-custo-entrega.ts:627-631`

**Issue:** The function is documented as preventing "texto livre da Uber...
de atravessar para o navegador (T-F21-07)", and its own test proves the
*exact* input string ("Rua Augusta, 123 - apto 45") doesn't appear verbatim
in the output — but the transform is just uppercase + strip
non-`[A-Z_]` characters, so `"Rua Augusta, 123"` becomes `"RUAAUGUSTA"`, which
is still a fully recognizable, greppable fragment of the original street
name (per the module's own second test). This is fine as a formatting guard
for the expected closed vocabulary of Uber fee codes (`FLAT_FEE`,
`BUSY_AREA_FEE`, …), but the comment overstates what it defends against —
worth tightening the comment or, if genuinely defending against PII leakage,
switching to an actual allowlist of known fee codes instead of a
character-class filter.

**Fix:** Non-blocking; either soften the doc comment's claim or replace with
an allowlist (`Set` of known `fee_code`/`category` values, mapping anything
unrecognized to `"DESCONHECIDO"`) if this is meant to stop more than
formatting noise.

## Areas With No Findings

- **Cents↔reais conversion:** `converterCentavosParaReais` correctly rejects
  non-integers, negatives, `NaN`/`Infinity`, and non-number types; the
  division itself and its call sites are consistent (cents in, reais out,
  never mixed). No 100x-style bug found.
- **Token scope/reuse:** `uber-entrega.ts` correctly reuses `obterTokenUber`
  from `uber-auth.ts` with the `"eats.deliveries"` scope (not
  `"business.receipts"`), and correctly calls
  `limparEntradaCacheTokenUber(config.clientId, "eats.deliveries")` on a 401
  before a single retry — matching the existing pattern in `uber.ts`
  exactly.
- **Authorization:** The route's `session.role !== "admin"` check matches
  the established pattern (`src/app/api/admin/backfill-estoque/route.ts`)
  byte-for-byte in structure and status code.
- **Error leakage:** No path returns the raw Uber response body,
  `client_secret`, or access token to the client; verified against both the
  `interpretarCustoEntregaUber` failure branches and the
  `mensagemFalhaCustoUber`/`mensagemMotivoGravacao` fixed-vocabulary
  message functions. `console.error` calls that do log the raw Uber body
  are server-side only and explicitly never log `config` (credentials).
- **Double-counting in the DRE:** Confirmed the write path only ever touches
  `Venda.custoEnvio`, never creates a `Despesa` row — matches
  `finance.ts`'s existing `freteReal` aggregation and is covered by an
  explicit test (`Teste 13`).
- **Idempotency via the unique index for the common case:** Two requests for
  the identical `(vendaId, deliveryId, result)` triple are safely idempotent
  (second write is a no-op re-application of the same value); a genuine
  cross-venda collision on the same `deliveryId` is correctly caught via
  `P2002` and mapped to `409 entrega_ja_lancada` (see WR-01 for the narrower
  same-delivery/different-outcome race that isn't covered).
- **Missing `await`:** No missing `await` found in either new module or the
  route handler.
